# 军用软件标书合规检验智能体技术方案（v2.0 · 能力自适应架构）

> **能力自适应多模型架构** — 同一套 CLI 工具，根据后端模型能力自动切换执行策略，确保弱模型不崩溃、强模型不被限制。
>
> v1.0 架构文档见 [军用软件标书合规检验智能体技术方案 v1.md](军用软件标书合规检验智能体技术方案 v1.md)，本文档描述 v2.0 的能力自适应升级方案。

---

## 一、问题诊断：v1.0 架构为何限制强模型

### 1.1 v1.0 架构回顾

v1.0 采用 **4 智能体 + Python 代码硬编排** 的架构：

```
用户上传文件 → ORA 调度 → DPA Round1（审查基准提取）
                         → 等待用户确认
                         → DPA Round2（字段护照提取）
                         → BCA + FCA 并行审查
                         → ORA 编译报告
```

代码层承担了：状态机流转、格式校验前置、重试反馈闭环、强制输出模板注入。LLM 只负责"填空"。

### 1.2 这套架构对 Qwen 27b 是必要的

Qwen 27b 的核心短板：
- **无法自主规划**：不能将一个复杂任务自行拆解为子步骤
- **长文注意力稀释**：上下文中段会丢失结构约束
- **输出格式不稳定**：Markdown 表格、章节编号容易出错
- **判定边界模糊**：面对"文件缺失 vs 扫描件无法提取"等边界场景容易误判

代码硬编排解决了这些问题——状态机保证流程正确，格式校验拦截错误输出，重试机制修正不稳定。

### 1.3 但这对 DeepSeek V4 / Claude Opus 是"枷锁"

强模型具备的能力，在 v1.0 架构下被闲置甚至抑制：

| 强模型能力 | v1.0 架构的实际影响 | 能力浪费程度 |
|-----------|-------------------|------------|
| **自主规划与任务分解** | ORA 状态机代替了模型自行规划，模型退化为被动执行者 | ★★★★★ 完全闲置 |
| **长上下文全局一致性** | 精准上下文投喂刻意限制了输入量，模型无法利用全局视角交叉验证 | ★★★★ 严重限制 |
| **结构化输出的稳定性** | 强制模板注入是对模型的"不信任"，反而可能干扰其自身的格式组织能力 | ★★★ 约束过度 |
| **判定边界的自主推理** | 硬编码的决策树（如"提取为空+文件清单存在→WARNING"）限制模型用自己的推理链 | ★★★★ 抑制推理 |
| **跨文档深度关联** | 文件被拆分投喂给不同 Agent，模型失去了跨文档发现隐性关联的机会 | ★★★★★ 信息割裂 |

**核心矛盾：为弱模型设计的"脚手架"，对强模型变成了"牢笼"。**

## 二、v2.0 核心设计：能力自适应执行模式

### 2.1 设计原则

1. **能力检测而非模型绑定**：不硬编码模型名称，根据上下文窗口大小、已知 benchmark 能力等级自动选择执行模式
2. **模式可降级不可升级**：高能力模式失败时自动降级为低能力模式重试，反之则不允许（弱模型无法运行强模式）
3. **同一套 CLI，三种内部策略**：用户接口统一，内部执行逻辑按模式分化
4. **提示词按能力缩放**：强模式用"目标导向"提示词，弱模式用"步骤导向"提示词

### 2.2 三档执行模式

```
┌──────────────────────────────────────────────────────────────┐
│                    Baguwen CLI (统一入口)                      │
│                  baguwen review --tender X --bid Y            │
└──────────────────────────┬───────────────────────────────────┘
                           │
                    ┌──────▼──────┐
                    │  能力检测    │
                    │  (自动/手动) │
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ MODE A        │  │ MODE B        │  │ MODE C        │
│ 编排模式       │  │ 半自治模式     │  │ 自治模式       │
│               │  │               │  │               │
│ 适用：        │  │ 适用：        │  │ 适用：        │
│ Qwen 27b     │  │ Qwen 70b     │  │ DeepSeek V4  │
│ 小型开源模型  │  │ 中等商用模型   │  │ Claude Opus  │
│               │  │               │  │ GPT-5 等     │
│ 策略：        │  │ 策略：        │  │ 策略：        │
│ 代码控制流程  │  │ 代码提供框架  │  │ 模型自主规划  │
│ LLM只写内容   │  │ LLM参与编排   │  │ 代码仅做校验  │
│ 强校验+重试   │  │ 中等校验      │  │ 轻校验       │
└───────────────┘  └───────────────┘  └───────────────┘
```

### 2.3 各模式详细定义

#### MODE A — 编排模式（Orchestrated）

**定位**：完全继承 v1.0 架构。代码控制一切流程，LLM 只负责内容生成。

```
DPA Round1 → [用户确认] → DPA Round2 → BCA + FCA (并行) → ORA 编译
    ↑                        ↑               ↑                  ↑
 代码调度                 代码调度        代码调度          代码调度+格式校验+重试
```

**关键特征**：
- 四智能体独立调用，上下文精准投喂
- 每次 LLM 输出后代码级格式校验，不通过即重试（最多 3 次）
- 系统提示词包含完整的判定边界、决策树、正误对照表
- 状态机硬编码，不允许模型跳过任何步骤
- 文件截断到 15,000 字符以内

#### MODE B — 半自治模式（Semi-Autonomous）

**定位**：保留多智能体分工，但合并冗余步骤，减少代码干预，扩大单次上下文窗口。

```
DPA (单轮，全量提取) → BCA + FCA (并行审查) → ORA 编译
         ↑                    ↑                    ↑
    代码调度              代码调度             格式校验+1次重试
```

**关键变化（相对于 MODE A）**：
- DPA 合并为单轮：审查基准 + 字段护照一次性提取（利用更大上下文）
- BCA/FCA 系统提示词删减 40%（移除决策树，保留核心规则）
- 格式校验保留但重试降为 1 次
- 文件截断提升到 30,000 字符
- 用户确认步骤改为可选的 `--auto-confirm` 标志

#### MODE C — 自治模式（Autonomous）

**定位**：将完整的 PRD 指令手册作为系统提示词注入，由模型自行规划全部执行步骤。代码只负责：传入文件、接收输出、最终质量校验。

```
┌─────────────────────────────────────────┐
│  单次/两次 LLM 调用                       │
│                                          │
│  System: PRD 完整指令手册 (~15K tokens)   │
│  User: 招标文件 + 投标文件              │
│                                          │
│  模型自行决定：                           │
│  - 是否需要分步提取                       │
│  - 审查顺序和深度                         │
│  - 报告组织方式                           │
│  - 何时标注"需人工复核"                   │
│                                          │
│  → 输出：完整审查报告                     │
└─────────────────────────────────────────┘
         │
         ▼
  ┌──────────────┐
  │ 代码层轻校验   │
  │ - 章节完整性   │
  │ - 附录A-G     │
  │ - AI痕迹      │
  │ - 投标建议存在 │
  │ (不重试，仅报告)│
  └──────────────┘
```

**关键特征**：
- **不做内容截断**：强模型有足够的上下文窗口（DeepSeek V4: 128K, Claude Opus: 200K），全文喂入
- **不做步骤分解**：系统提示词描述审查目标和标准，不规定执行步骤
- **不做判定边界硬编码**：删除所有决策树和场景分支规则，让模型自主推理
- **不做强制模板注入**：仅描述报告应包含哪些章节和附录，不规定具体表格列名和 Markdown 结构
- **轻校验不阻塞**：代码校验结果作为质量报告输出，不触发自动重试
- **双轮可选模式**：对于超大文件集（50+ 文件），可降级为两轮调用——第一轮生成审查计划供用户确认，第二轮执行并输出报告

**MODE C 系统提示词示意（精简版）**：

```markdown
你是军用软件标书合规审查专家。请阅读招标文件和投标文件，按以下标准完成审查并输出报告。

## 审查维度（强制覆盖）
1. 废标红线审查：资格准入9项、★条款响应对撞、保证金与授权、反串通筛查、形式要件
2. 中标胜算评估：商务响应得分预测、技术方案专业度、经济合理性
3. 隐蔽风险探测：暗标脱敏彻底性、数据勾稽关系
4. 电子文件安检：PDF合规、扫描件质量、电子签章、文件命名

## 报告结构（强制输出）
- 第一部分到第七部分（略，见PRD完整描述）
- 附录A-G（必须全部生成）

## 判定规则
- 每个否决项须引用招标条款原文
- 无法从电子文件判定的标注"需人工复核"
- 报告中不得出现"智能体""AI审查"等表述
- 投标建议必须三选一：建议递交/有条件递交/不建议递交

## 审查方法论
（嵌入 PRD 第二章四维审查模型的完整知识体系）
```

### 2.4 模式自动选择逻辑

```
输入: model_id (str), context_window (int), user_mode_override (Optional[str])

1. 用户显式指定 --mode  → 使用指定模式
2. 用户未指定:
   a. context_window >= 100K AND model 在强模型白名单 → MODE C
   b. context_window >= 32K AND model 在中模型白名单 → MODE B
   c. 其他 → MODE A (安全默认值)

强模型白名单: deepseek-v4, claude-opus, claude-sonnet, gpt-5, gpt-4o, gemini-2.5
中模型白名单: qwen-70b, qwen-72b, llama-70b, deepseek-v3, claude-haiku
默认兜底: MODE A

降级触发:
- MODE C 输出质量分 < 60 → 自动降级 MODE B 重试
- MODE B 输出质量分 < 60 → 自动降级 MODE A 重试
- 降级时打印 warning 提示用户
```

## 三、CLI 工具设计

### 3.1 命令接口

```bash
# 基础用法（自动检测模式）
baguwen review --tender ./tender.pdf --bid ./bid_files/

# 显式指定模式
baguwen review --tender ./tender.pdf --bid ./bid_files/ --mode autonomous

# 指定模型
baguwen review --tender ./tender.pdf --bid ./bid_files/ --model deepseek/deepseek-v4

# 恢复中断的审查
baguwen review --resume ./output/case1/case1-pipeline_state.json

# 仅重新编译报告（不重新审查）
baguwen review --recompile --baseline ./baseline.md --bca ./bca.md --fca ./fca.md

# 自循环评估模式
baguwen evaluate --project case1 --rounds 5 --model qwen/qwen3.6-27b
```

### 3.2 配置文件

```toml
# config/pipeline.toml

[models]
# 默认模型（可通过 --model 覆盖）
default = "qwen/qwen3.6-27b"

[mode]
# auto | orchestrated | semi-autonomous | autonomous
default = "auto"
# 自动降级开关
auto_degradation = true

[validation]
# 编排模式重试次数
orchestrated_max_retry = 3
# 半自治模式重试次数
semi_autonomous_max_retry = 1
# 自治模式：仅报告不重试
autonomous_retry = false

[context]
# 编排模式单文件截断阈值（字符）
orchestrated_truncate = 15000
# 半自治模式截断阈值
semi_autonomous_truncate = 30000
# 自治模式不截断
autonomous_truncate = 0

[output]
dir = "./output"
```

## 四、提示词策略对比

### 4.1 提示词复杂度按模式缩放

| 提示词特征 | MODE A (编排) | MODE B (半自治) | MODE C (自治) |
|-----------|-------------|----------------|--------------|
| 系统提示词长度 | 200-300 行/Agent | 100-150 行/Agent | 400-600 行（合并） |
| 判定边界决策树 | 完整包含 | 仅关键场景 | 不包含 |
| 正误对照表 | 包含 | 包含 | 不包含 |
| 输出格式模板 | 强制注入（具体表格列名） | 结构描述（章节要求） | 目标描述（应含内容） |
| 文件索引 | 强制构建 | 包含 | 模型自主决定 |
| 字数预算 | 每节标注最低字数 | 仅总览标注 | 不标注 |
| 禁用词表 | 完整列表 | 核心禁用词 | 一句话原则说明 |
| 审查方法论 | 摘要（核心规则） | 完整方法论 | 嵌入 PRD 全文 |

### 4.2 为什么强模型不需要"过度指导"

**反直觉的发现**：对强模型而言，过度精确的指令反而降低输出质量。

```
弱模型需要:  "请输出表格，列名必须是 | 检查项 | 招标要求 | 标书实际 | 判定 |"
强模型需要:  "逐项检查并输出判定结果"

原因: 强模型已经内化了"专业审查报告的表格应该如何组织"，
      硬编码的列名限制可能与其内部最优方案冲突。
```

**关键原则**：提示词的精确度应与模型能力**反比**。越弱的模型需要越精确的指令；越强的模型需要越多的"自由度"来发挥其推理能力。

## 五、质量校验策略对比

### 5.1 校验严格度按模式缩放

| 校验项 | MODE A | MODE B | MODE C |
|--------|--------|--------|--------|
| 格式校验 | **阻塞性**：不通过则重试 | **警告性**：记录但不阻塞，1次重试 | **仅报告**：输出质量报告，不重试 |
| 章节完整性 | 7部分+附录A-G缺一不可 | 7部分+附录A-G缺一不可 | 章节缺失计入质量分但不阻塞 |
| AI痕迹检测 | 零容忍（每处-15分） | 零容忍（每处-15分） | 零容忍（每处-10分，仅警告） |
| 表格数量 | ≥8行，≥3个表 | ≥6行，≥3个表 | 不检查具体数量 |
| 报告长度 | ≥1500字符 | ≥1000字符 | ≥500字符（仅防空输出） |
| 投标建议 | 必须三选一 | 必须三选一 | 必须三选一 |
| 否决项计数 | 与BCA/FCA结果交叉验证 | 交叉验证 | 不交叉验证（信任模型） |

### 5.2 降级触发条件

```
if mode == MODE_C:
    quality = validate_report_quality(report)
    if quality.score < 60:
        log.warning(f"自治模式报告质量{quality.score}分，自动降级为半自治模式")
        return run_mode_b(tender, bid)  # 降级重试

if mode == MODE_B:
    quality = validate_report_quality(report)
    if quality.score < 60:
        log.warning(f"半自治模式报告质量{quality.score}分，自动降级为编排模式")
        return run_mode_a(tender, bid)  # 降级重试
```

## 六、模式选择决策指南

### 6.1 按场景推荐

| 使用场景 | 推荐模式 | 理由 |
|---------|---------|------|
| Qwen 27b 运行 | MODE A | 模型能力不足，必须代码编排 |
| Qwen 70b 运行 | MODE B | 可减少编排开销，但仍需结构约束 |
| DeepSeek V4 运行 | MODE C | 充分发挥模型自主规划能力 |
| Claude Opus 运行 | MODE C | 同上 |
| 快速原型验证 | MODE C | 最快获得完整报告 |
| 生产环境（高可靠性要求） | MODE A | 每个步骤可审计、可复现、可单独重试 |
| A/B 测试不同模型 | 各模型默认模式 + 统一质量评分对比 | 公平对比模型能力 |
| 批量处理（多项目并行） | MODE A 或 B | 状态持久化支持断点恢复 |

### 6.2 成本-质量权衡

```
MODE C (自治)   →  最低成本（1次LLM调用）   →  质量方差最大（依赖模型能力）
MODE B (半自治) →  中等成本（3次LLM调用）   →  质量方差中等
MODE A (编排)   →  最高成本（6次LLM调用+重试）→  质量最稳定（代码护航）
```

## 七、v1.0 → v2.0 迁移路径

### Phase 1: 抽象层引入（不影响当前功能）
- 创建 `modes/base.py` 抽象基类
- 将当前 `pipeline.py` 重构为 `modes/orchestrated.py`（行为完全不变）
- 添加 `cli/main.py` 和 `mode_selector.py`

### Phase 2: MODE B 实现
- 合并 DPA 两轮为单轮
- 精简 BCA/FCA 提示词
- 实现降级逻辑

### Phase 3: MODE C 实现
- 编写合并版系统提示词 `mode_c/reviewer.md`
- 实现单/双轮自治调用
- 轻校验报告生成

### Phase 4: 评估与收敛
- 用自循环评估对比 MODE A vs MODE C 在 DeepSeek V4 上的表现
- 验证"强模型在 MODE C 下质量不低于 MODE A"的核心假设

## 八、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| MODE C 下强模型产生幻觉（编造不存在的否决项） | 报告可信度 | 交叉验证开关：`--cross-validate` 标志启用 BCA/FCA 独立审查与 ORA 报告对比 |
| 模式自动选择误判（弱模型选了 MODE C） | 输出崩溃 | 白名单机制 + 输出质量分 < 30 时硬降级 |
| MODE C 的报告格式与 MODE A 不一致 | 用户体验不一致 | 统一质量校验器对三种模式输出做相同结构检查 |
| 过多模式增加维护成本 | 代码复杂度 | 共享核心模块（models, validator, context_builder），模式间仅调用策略不同 |

## 九、附录：与 biddings-writer 的架构对比

| 维度 | biddings-writer (v1.0) | biddings-reviewer (v2.0) |
|------|----------------------|-------------------------|
| 任务性质 | 生成型（大纲+正文撰写） | 分析型（合规审查） |
| 输出稳定性要求 | 中等（人工审核兜底） | 极高（否决项遗漏=致命） |
| 多模型策略 | 单一流程，提示词强化 | 三档模式自适应 |
| 降级机制 | 格式修正重试 | 模式降级 + 格式修正重试 |
| 状态持久化 | 无（一次性生成） | 有（支持断点恢复） |
| 用户交互 | 无（批量生成） | MODE A 需确认审查基准 |

---

> **核心结论：v2.0 不是推倒重来，而是在 v1.0 稳定的编排能力之上，为强模型"松绑"——让 DeepSeek V4 之类的大模型可以跳过脚手架直接用其自身能力完成审查，同时保留弱模型的代码护航。**
