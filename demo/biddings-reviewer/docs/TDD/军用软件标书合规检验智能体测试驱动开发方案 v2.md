# 军用软件标书合规检验智能体测试驱动开发方案（v2.0 · 能力自适应架构测试方案）

> **多模型能力自适应架构的测试策略**。配合 PRD [军用软件标书合规检验智能体指令手册](../PRD/军用软件标书合规检验智能体指令手册.md) 和 [军用软件标书合规检验智能体技术方案 v2.md](./军用软件标书合规检验智能体技术方案 v2.md) 共同驱动开发。
>
> v2.0 核心命题：**同一套 CLI，三种内部策略，如何验证每一种都正确？如何确保强模型不被架构限制？**

---

## 一、v2.0 测试的核心变化

### 1.1 v1.0 → v2.0 测试策略演进

| 维度 | v1.0（单模型优化） | v2.0（多模型自适应） |
|------|-------------------|---------------------|
| **测试对象** | 仅 Qwen 27b 的输出质量 | Qwen 27b / 70b / DeepSeek V4 / Claude Opus 各自在对应模式下的输出 |
| **成功标准** | "27b 追平 DeepSeek V4" | "每种模型在最适合的模式下达到其能力上限" |
| **质量评估** | 单一黄金标准对照 | 多基线对照——容忍强模型有不同于黄金标准的但同样合理的审查路径 |
| **回归风险** | 改动提示词 → 27b 输出变差 | 改动提示词/模式切换逻辑 → 某个模型的某个模式退化 |
| **新增测试维度** | — | 模式选择正确性、降级触发正确性、跨模式质量一致性 |
| **API 成本** | 中等（单模型×多轮） | 高（多模型×多模式×多轮），需分层控制 |

### 1.2 核心测试原则

1. **不要求不同模式产生相同输出**：MODE C 的报告可能比 MODE A 更精炼（少 30% 字数），不应因为"与黄金标准不一致"扣分——只要审查结论正确即可
2. **分层控制 API 成本**：代码级测试（0 成本）→ 单模型单元质量测试（中等成本）→ 跨模型对比测试（高成本，按需触发）
3. **模式降级是正确行为，不是失败**：MODE C 输出质量不达标后自动降级到 MODE B 并成功，这是架构正确的表现
4. **强模型在 MODE C 下的审查结论必须不低于 MODE A**：这是 v2.0 架构的核心验证目标

## 二、测试分层（v2 扩展）

```
         ┌──────────────────────────────────────────┐
         │  跨模型对比评估 (Cross-Model Evaluation)   │  Claude Judge + 多模型并行
         │  --model all --mode auto --rounds 3       │  验证：强模型MODE C ≥ 弱模型MODE A
        ┌┴──────────────────────────────────────────┴┐
        │   单模型自循环评估 (Per-Model Loop)          │  指定模型×指定模式×N轮
        │   baguwen evaluate --model X --mode Y       │  收敛速度 / 最佳轮数
       ┌┴──────────────────────────────────────────┴┐
       │    质量测试 - API 级 (Quality Tests)          │  每种模式×1轮真实调用
       │    test_reviewer_mode_a/b/c.py               │  格式+内容+AI痕迹 验收
      ┌┴──────────────────────────────────────────┴┐
      │    集成测试 - 模式切换 (Integration Tests)      │  模式选择/降级/CLI 行为
      │    test_mode_selector.py / test_degradation.py │  不调用 LLM，mock client
     ┌┴──────────────────────────────────────────┴┐
     │    单元测试 - 纯代码 (Unit Tests)              │  数据模型/状态机/校验器
     │    tests/unit/ (同v1.0 + 模式测试)            │  秒级，0 API 费用
    └──────────────────────────────────────────────┘
```

### 2.1 各层职责与运行频率

| 层级 | 运行条件 | 频率 | 耗时 | API 费用 |
|------|---------|------|------|---------|
| 单元测试 | 每次提交 | 必跑 | <5秒 | $0 |
| 集成测试 | 每次提交 | 必跑 | <30秒 | $0 |
| 质量测试-API | PR / 发版前 | 手动触发 | 5-15分钟 | ~$2-5 |
| 自循环评估 | prompt 变更后 | 手动触发 | 30-60分钟 | ~$10-30 |
| 跨模型对比 | 架构变更后 | 手动触发 | 1-2小时 | ~$30-80 |

        """DeepSeek V4 自动选择自治模式"""

        """未知模型安全降级为编排模式"""

        assert result.degraded_from == ReviewMode.AUTONOMOUS
        assert result.quality_score >= 60

    def test_mode_b_degraded_when_score_low(self, mock_llm_client):
        """MODE B 输出质量分 < 60 自动降级 MODE A"""
        mock_llm_client.set_response("incomplete report...")
        runner = ReviewRunner(mode=ReviewMode.SEMI_AUTONOMOUS)
        result = runner.run(TENDER_DOC, BID_DOCS)
        assert result.mode_used == ReviewMode.ORCHESTRATED
        assert result.degraded_from == ReviewMode.SEMI_AUTONOMOUS

    def test_mode_a_no_further_degradation(self, mock_llm_client):
        """MODE A 是最低档，不再降级——即使低分也接受"""
        mock_llm_client.set_response("very short...")
        runner = ReviewRunner(mode=ReviewMode.ORCHESTRATED)
        result = runner.run(TENDER_DOC, BID_DOCS)
        assert result.mode_used == ReviewMode.ORCHESTRATED
        assert result.degraded_from is None
        # MODE A 内部仍有重试机制（3次），重试耗尽后接受最终输出

    def test_degradation_preserves_inputs(self, mock_llm_client):
        """降级时输入文件不丢失"""
        runner = ReviewRunner(mode=ReviewMode.AUTONOMOUS)
        result = runner.run(TENDER_DOC, BID_DOCS)
        # 降级后应依然基于相同的招标文件和投标文件
        assert result.tender_doc == TENDER_DOC
        assert result.bid_docs == BID_DOCS

    def test_auto_degradation_disabled_flag(self, mock_llm_client):
        """--no-auto-degrade 标志禁用自动降级"""
        mock_llm_client.set_response("low quality...")
        runner = ReviewRunner(
            mode=ReviewMode.AUTONOMOUS,
            auto_degrade=False
        )
        result = runner.run(TENDER_DOC, BID_DOCS)
        assert result.mode_used == ReviewMode.AUTONOMOUS  # 未降级
        assert result.quality_score < 60  # 接受低分

        assert quality["score"] >= 80, f"MODE C 报告质量: {quality}"

    def test_review_conclusions_correct(self, mode_c_result):
        """审查核心结论正确——这是最重要的断言"""
        report = mode_c_result.report
        # 必须检出黄金标准中的所有否决项
        gold_items = extract_rejections(GOLD_REPORT)
        actual_items = extract_rejections(report)
        missed = gold_items - actual_items
        assert len(missed) == 0, f"MODE C 遗漏否决项: {missed}"

        report = mode_c_result.report
        gold_items = extract_rejections(GOLD_REPORT)
        actual_items = extract_rejections(report)
        false_positives = actual_items - gold_items
        # 允许合理的新发现（可能黄金标准未覆盖），但须有证据
        for fp in false_positives:
            assert has_evidence_chain(report, fp), \
                f"MODE C 产生了无证据的否决项: {fp}"

    def test_no_ai_traces(self, mode_c_result):

## 五、自循环评估框架（v2 扩展）

### 5.1 多模型多模式评估矩阵

```bash
# 单模型单模式（v1.0 继承）
baguwen evaluate --model qwen/qwen3.6-27b --mode orchestrated --rounds 5

# 单模型全模式对比
baguwen evaluate --model deepseek/deepseek-v4 --mode all --rounds 3

# 跨模型对比（核心评估场景）
baguwen evaluate --model all --mode auto --rounds 3 --project case1

# 降级链路验证
baguwen evaluate --model qwen/qwen3.6-27b --mode autonomous --expect-degradation
```

### 5.2 评估维度（v2 扩展 — 新增 D6）

在 v1.0 的 5 维度（D1-D5）基础上新增：

| 维度 | 权重 | 评分标准 | v1→v2 变化 |
|------|------|---------|-----------|
| D1：审查完整度 | 30% | 同 v1.0 | 不变 |
| D2：判定准确性 | 25% | 同 v1.0 | 不变 |
| D3：报告结构规范性 | 20% | 同 v1.0 | 不变 |
| D4：建议可操作性 | 15% | 同 v1.0 | 不变 |
| D5：AI 痕迹零检出 | 10% | 同 v1.0 | 不变 |
| **D6：模式适配效率** | **额外加分项** | **新增** — 用更少的 API 调用和更短的时间达到同等质量 | +5 分加成 |

**D6 评分标准**：
- 5 分（+5 加成）：MODE C 在 ≤2 次调用内达到 ≥90 质量分
- 3 分（+3 加成）：MODE B 在 ≤3 次调用内达到 ≥85 质量分
- 1 分（+1 加成）：任何模式的降级都成功恢复
- 0 分：重试或降级未改善质量

## 六、收敛标准（按模型能力等级）

### 6.1 分级收敛目标

不再要求所有模型达到同一标准——按模型能力设定合理预期：

| 指标 | Qwen 27b (MODE A) | Qwen 70b (MODE B) | DeepSeek V4 (MODE C) |
|------|-------------------|-------------------|----------------------|
| 整体平均分 | ≥ 4.0 / 5.0 | ≥ 4.3 / 5.0 | ≥ 4.5 / 5.0 |
| 审查完整度（D1） | ≥ 4.5 | ≥ 4.5 | ≥ 5.0 |
| 判定准确性（D2） | ≥ 4.0 | ≥ 4.0 | ≥ 4.5 |
| AI 痕迹零检出 | ≥ 4.5 | ≥ 5.0 | ≥ 5.0 |
| 否决项遗漏率 | 0% | 0% | 0%（红线，所有模式通用） |
| 格式合规率 | ≥ 95% | ≥ 90% | ≥ 85% |
| API 调用次数 | ≤ 10 | ≤ 5 | ≤ 2 |
| 平均耗时 | ≤ 6 min | ≤ 3 min | ≤ 1 min |

### 6.2 验证"强模型不被限制"的四项硬指标

| 验证项 | 方法 | 判定标准 |
|--------|------|---------|
| **效率释放** | 对比同一模型 MODE C vs MODE A 的 API 调用次数 | MODE C 调用次数 ≤ MODE A 的 50% |
| **质量不降** | 对比同一模型 MODE C vs MODE A 的审查完整度和判定准确性 | MODE C ≥ MODE A |
| **推理自主** | 检查 MODE C 报告是否展现了 MODE A 模板未规定的分析维度 | 至少出现 1 处超出模板的自主分析 |
| **成本优势** | 对比达到相同质量所需的总 API 费用 | MODE C 成本 ≤ MODE A 的 60% |

## 八、CI/CD 集成

### 8.1 GitHub Actions 工作流

```yaml
# .github/workflows/test.yml
name: Test

on:
  push:
    branches: [master, main]
  pull_request:
    branches: [master, main]

jobs:
  unit-and-integration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -e ".[dev]"
      - name: Unit tests
        run: pytest tests/unit/ -v --tb=short
      - name: Integration tests (mode selector, CLI, degradation)
        run: pytest tests/integration/ -v --tb=short

  quality-api:
    needs: unit-and-integration
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    strategy:
      matrix:
        test-suite: [mode_a, mode_b]
        # MODE C 仅在手动触发时运行（成本控制）
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -e ".[dev]"
      - name: Quality tests (${{ matrix.test-suite }})
        env:
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
        run: pytest tests/quality/ -m "${{ matrix.test-suite }} and api" -v --tb=long

  cross-model-evaluation:
    needs: unit-and-integration
    if: github.event_name == 'workflow_dispatch'  # 仅手动触发
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install -e ".[dev]"
      - name: Cross-model comparison
        env:
          OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
        run: baguwen evaluate --model all --mode auto --rounds 1 --project LZ270
```

### 8.2 成本控制策略

| 触发条件 | 运行内容 | 预估费用 |
|---------|---------|---------|
| 每次 push | 单元测试 + 集成测试 | $0 |
| PR 创建 | MODE A + MODE B 质量测试 | ~$3 |
| PR 合并到 main | 同 PR | ~$3 |
| 手动触发 `cross-model-evaluation` | 全部模型全部模式 | ~$40 |
| 发版前 | 自循环评估 × 3 轮 | ~$25 |

## 十、pytest 标记体系（v2 扩展）

```ini
[tool.pytest.ini_options]
markers = [
    # v1.0 继承
    "api: 需要真实 API 调用",
    "claude: 需要 Claude API（Judge 评估）",
    "slow: 运行超过 30 秒",
    "dpa: DPA Agent 专项",
    "bca: BCA Agent 专项",
    "fca: FCA Agent 专项",
    "ora: ORA Agent 专项",
    # v2.0 新增
    "mode_a: MODE A (编排模式) 专项",
    "mode_b: MODE B (半自治模式) 专项",
    "mode_c: MODE C (自治模式) 专项",
    "degradation: 降级逻辑测试",
    "cli: CLI 接口测试",
    "cross_model: 跨模型对比测试",
    "expensive: 高成本测试（手动触发）",
]
```

**常用运行命令（v2 新增）：**

```bash
# 仅 MODE A 测试（最常用）
pytest tests/ -v -m "mode_a or not api"

# 仅降级逻辑测试（无 API）
pytest tests/unit/test_degradation.py -v

# MODE C 专项（需 API + 强模型）
pytest tests/quality/test_reviewer_mode_c.py -m "mode_c and api" -v --tb=long

# 全模式回归（发版前）
pytest tests/unit/ tests/integration/ -v && \
  pytest tests/quality/ -m "api and not expensive" -v

# 跨模型对比（架构变更后，手动触发）
pytest tests/quality/ -m "cross_model" -v --tb=long
```
