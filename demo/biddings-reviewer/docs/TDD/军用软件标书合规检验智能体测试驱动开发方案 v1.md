# 军用软件标书合规检验智能体测试驱动开发方案（v1.0 · Qwen3.6 27B）

> 面向"27B 追平 DeepSeek V4"目标的验证策略。配合 PRD [军用软件标书合规检验智能体指令手册](../PRD/军用软件标书合规检验智能体指令手册.md) 共同驱动开发。
>
> 核心策略：**代码级检查秒级验证 → 单元测试验证逻辑 → API 调用验证 Agent 产出 → Claude-as-Judge 多轮迭代评估报告质量**。

---

## 一、小模型适配核心策略

DeepSeek V4 等大参数模型可在宽泛提示下自主规划审查流程、保持长报告一致性、稳定输出结构化内容。27B 模型无法做到这些，但可通过**工程设计**弥补能力差距：

| 策略 | 解决的问题 | 实现方式 |
|------|-----------|---------|
| **精准上下文投喂** | 注意力稀释导致关键信息被忽略 | DPA 每次只传入当前轮次所需文档；BCA 只传 baseline+extracted_fields；FCA 只传 bid_text+extracted_fields；ORA 只传各维度摘要 |
| **代码控制流程** | 小模型难以同时规划和执行 | 状态机、路由、重试、格式校验全部由 Python 代码完成，LLM 只写内容 |
| **强制输出模板注入** | 小模型长文中段会丢失结构 | 每个 Agent 的 system prompt 末尾强制注入"输出格式"章节，用具体表格列名和 Markdown 结构约束 |
| **单次双维度 Agent** | 拆分多次调用成本高且上下文割裂 | BCA 一次调用同时完成废标红线+中标胜算；FCA 一次调用同时完成隐蔽风险+电子文件安检 |
| **代码级格式前置校验** | 小模型输出格式不稳定 | 每次 LLM 输出后先经过 regex+keyword 格式校验，格式不通过直接构造修正 prompt 重试，不进入下一阶段 |

### 1.1 设计原则

1. **流程由代码控制，内容由模型生成**：状态机、路由、重试计数、格式校验、报告评分全部为 Python 代码；LLM 只负责提取信息、审查内容、编译报告。
2. **完整还原 PRD 四阶段方案**：DPA Round1 → DPA Round2 → BCA+FCA 并行 → ORA 编译报告。
3. **精准上下文投喂**：每个 Agent 调用只传入该 Agent 需要的信息，不传无关上下文，降低注意力稀释。
4. **可配置模型**：所有模型名称通过 `.env` 配置，不硬编码，便于切换和 A/B 测试。

## 二、测试分层

```
         ┌──────────────────────────────────┐
         │  自循环质量评估（多轮）              │  Claude Sonnet 4.6 Judge + 迭代追踪
         │  python evaluate.py --loop         │  5维度评分 × N轮
        ┌┴──────────────────────────────────┴┐
        │   质量测试（真实 API）               │  DPA单轮 / BCA单维 / FCA单维 / 完整报告
        │   pytest -m api                     │  Qwen 27B 真实调用，格式+内容双验收
       ┌┴──────────────────────────────────┴┐
       │    单元测试（纯代码，零API费用）        │  数据模型 / 状态机 / Prompt构建 / 格式校验
       │    pytest tests/unit/                │  秒级跑完，提交前必须全绿
      └──────────────────────────────────────┘
```

**层级职责：**
- **代码级检查**：静态格式校验 + prompt 完整性 — 内嵌在 pipeline 和 context_builder 中
- **单元测试**：验证数据模型、状态机、Prompt 构建、格式校验逻辑 — 完全不调用 LLM
- **质量测试**：验证真实 27B 模型输出是否满足结构和内容要求 — 消耗 API
- **自循环评估**：多轮运行流水线，用 Claude Judge 评分，识别最弱维度，生成 prompt 改进建议

## 三、迭代开发路线（6阶段）

每阶段流程：**写测试 → 红灯 → 写实现 → 绿灯 → 提交**

| 阶段 | 名称 | 主要测试文件 | 主要实现文件 | 验收标准 |
|------|------|------------|------------|---------|
| **Phase 1** | Foundation | `test_models.py` | `models.py` | ReviewPhase/ReviewVerdict/RiskLevel 枚举正确；PipelineState 序列化往返一致；VALID_TRANSITIONS 合法转换通过 |
| **Phase 2** | 编排基础设施 | `test_state.py`, `test_format_validator.py`, `test_context_builder.py` | `state.py`, `context_builder.py`, `format_validator.py` | 原子写入无冲突；DPA/BCA/FCA/ORA 四类 prompt 完整性检查通过；格式校验覆盖各 Agent 类型 |
| **Phase 3** | Agent 客户端与配置 | `test_options.py`, `test_client.py` | `client.py`, `options.py` | 四种 Agent Options 工厂正常；call_with_retry 重试/超时逻辑正确；模型从 .env 读取 |
| **Phase 4** | Pipeline 编排 | `test_pipeline.py` | `pipeline.py` | 四阶段状态转换正确；BCA+FCA 并行执行完成；重试/格式修正反馈闭环正确；报告质量自动评分 |
| **Phase 5** | API 质量测试 | `tests/quality/test_reviewer.py` | 全线（prompt 迭代） | DPA 提取完整率 ≥80%；BCA/FCA 判定明确率 ≥85%；报告结构完整率 ≥90%；AI 痕迹零检出 |
| **Phase 6** | 自循环优化 | `tests/quality/evaluate_pipeline.py` | 全线（prompt + pipeline 迭代） | 整体报告平均分 ≥3.5；否决项遗漏率 0%；重试成功率 ≥70% |

## 六、自循环质量评估框架（核心）

这是验证"27B 追平 DeepSeek V4"目标的主要工具。多轮运行流水线，每轮由 Claude Judge 评分，识别最弱维度，生成具体 prompt 改进建议，人工确认后进入下一轮。

### 6.1 评估流程

```
┌──────────────┐
│  运行流水线   │  python run_full_pipeline.py --project TEST
│  (Qwen 27B)  │
└──────┬───────┘
       │ 产出 review-report.md
       ▼
┌──────────────┐
│  评估引擎     │  python evaluate.py --project TEST
│  (Claude)    │  Claude Sonnet 4.6 作为 Judge
└──────┬───────┘
       │ 产出 evaluation_report.json
       ▼
┌──────────────┐
│  结果分析     │  识别最弱 2 个审查维度 + 5 维度分项得分
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  改进建议     │  Claude 分析低分原因 → 生成 prompt 改进建议
│  (Claude)    │  输出 improvement_suggestions.md
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  人工审核     │  确认改进方案
│  + 修改      │  修改 prompts/ 或 context_builder.py
└──────┬───────┘
       └─────────────────────────────────── 下一轮
```

### 6.2 评估维度（5维度 × 5分制）

| 维度 | 权重 | 评分标准 |
|------|------|---------|
| **D1：审查完整度** | 30% | ★条款提取是否完整、资格准入9项是否全覆盖、评分标准是否逐项提取。5分=100%覆盖，3分=≥80%，1分=<60% |
| **D2：判定准确性** | 25% | 否决项判定是否正确（不遗漏/不过度）、偏离状态判定是否符合招标原文、得分预测是否有依据。5分=零误判，3分=个别模糊，1分=严重误判或遗漏 |
| **D3：报告结构规范性** | 20% | 7部分结构是否完整、表格是否符合模板格式、图号表号是否正确。5分=完全规范，3分=基本规范个别缺漏，1分=严重缺失 |
| **D4：建议可操作性** | 15% | 投标建议是否基于充分证据、整改建议是否具体可执行、人工复核事项是否完整。5分=每项建议可操作，3分=部分建议笼统，1分=无实质建议 |
| **D5：AI 痕迹零检出** | 10% | 报告全文无"根据指令手册""智能体判断""按照SOP"等暴露AI审查身份的短语。5分=零检出，每检出1处扣1分 |

### 6.3 Judge System Prompt（`tests/quality/judge_system.md`）

```markdown
评分使用0-5分制，必须给出具体分数和简短理由。
禁止给出模糊评价，必须引用报告中的具体内容作为评分依据。
```

```
- 5分：投标建议有充分证据支撑、每条整改建议具体可执行、人工复核事项完整
- 3分：有建议但部分笼统
```
