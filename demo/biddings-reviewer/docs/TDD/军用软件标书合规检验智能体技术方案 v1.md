# 军用软件标书合规检验智能体技术方案（v1.0 · Qwen3.6 27B）

> 基于 Claude Agent SDK 的多智能体标书合规审查系统。目标：用 **Qwen3.6 27B**（OpenRouter）在标书合规检验任务上追平 DeepSeek V4 等大参数模型。
>
> 本文描述"实现什么"，配合 [军用软件标书合规检验智能体测试驱动开发方案 v1.md](军用软件标书合规检验智能体测试驱动开发方案 v1.md) 确定"怎么验证"。

---

## 一、小模型适配核心策略

DeepSeek V4 等大参数模型可以在宽泛提示下自主规划、交叉验证多份文件、稳定输出结构化报告。27B 模型做不到这些，但可以通过**工程设计**弥补能力差距：

| 策略 | 解决的问题 | 实现方式 |
|------|-----------|---------|
| **精准上下文投喂** | 注意力稀释导致关键信息被忽略 | DPA Round1 截断招标文件到 45K 字符；Round2 关键投标文件 ≤15K，其他 ≤4K；BCA/FCA 输入 ≤20K |
| **代码控制流程** | 小模型难以同时规划和执行 | 状态机、路由、重试、格式校验全部由 Python 代码完成，LLM 只写内容 |
| **强制输出模板注入** | 小模型长文中段会丢失结构 | 每个 Agent 的 system prompt 末尾强制注入输出格式（具体表格列名、Markdown 结构） |
| **单次双维度 Agent** | 拆分多次调用成本高且上下文割裂 | BCA 一次调用同时完成废标红线 + 中标胜算；FCA 一次调用同时完成隐蔽风险 + 电子文件安检 |
| **代码级格式前置校验** | 小模型输出格式不稳定 | 每次 LLM 输出后先经过 regex + keyword 格式校验，格式不通过则构造修正 prompt 重试（MAX_RETRY=3） |

### 1.1 设计原则

1. **流程由代码控制，内容由模型生成**：状态机、路由、重试计数、格式校验全部是 Python 代码；LLM 只负责提取信息、做出判定、撰写报告。
2. **完整还原 PRD 四阶段方案**：DPA Round1（招标解析）→ 人工确认 → DPA Round2（投标提取）→ BCA + FCA 并行审查 → ORA 编译报告。
3. **精准上下文投喂**：每个 Agent 调用只传入该 Agent 需要的信息，不传无关文件和冗余字段，降低注意力稀释。
4. **可配置模型**：所有模型名称通过 `.env` 配置，不硬编码，便于切换和 A/B 测试。

## 三、DPA 阶段设计（文档解析两轮方案）

### 3.1 两轮工作流

```
DPASession.run_round1(tender_doc)
  └─ 传入招标文件（截断到 45,000 字符）
  └─ 要求按 A/B/C/D 四类模板格式提取：
       A. ★号条款（逐条引用，判定能否负偏离）
       B. 资格准入条件（9项：保密/社保/纳税/审计...）
       C. 评分标准（商务/技术/价格三类分值分布）
       D. 格式与封装要求（文件命名/装订/盖章/签字）
  └─ 保存 {project_code}-review-baseline.md
  └─ [人工确认]（auto_confirm=False 时阻塞等待 stdin，
      用户可输入补充意见触发追加输出，Enter 直接确认）

DPASession.run_round2(baseline, bid_files)
  └─ 传入：审查基准（≤10K） + 文件清单索引 + 关键文件内容
       关键文件（招标指定格式文件）：每份 ≤15,000 字符
       其余文件：每份 ≤4,000 字符
  └─ 要求按字段护照模板逐字段提取：
       - 投标人基本信息（公司名/统一社会信用代码/法定代表人）
       - 资质证书（编号/等级/有效期）
       - ★条款逐条响应情况
       - 报价信息（总价/分项/澄清记录）
  └─ 保存 {project_code}-extracted_fields.json
```

**人工确认机制：** CLI 模式下从 stdin 读取，用户可输入修改意见触发 DPA 追加分析，直接 Enter 确认进入下一阶段。`auto_confirm=True` 时跳过确认，用于自动化测试。

### 3.2 上下文截断策略

| 阶段 | 文件类型 | 截断上限 | 设计理由 |
|------|---------|---------|---------|
| DPA Round1 | 招标文件 | 45,000 字符 | 覆盖典型招标文件全文；超出部分为附件正文，基准条款通常在前半部分 |
| DPA Round2 | 关键投标文件 | 15,000 字符/份 | 覆盖资质证书、承诺函等关键格式文件全文 |
| DPA Round2 | 普通投标文件 | 4,000 字符/份 | 提取文件头部基本信息即可，无需全文 |
| DPA Round2 | 审查基准（注入） | 10,000 字符 | 防止 Round2 Prompt 超过 27B 有效上下文 |
| BCA / FCA 输入 | 审查基准 | 10,000 字符 | — |
| BCA / FCA 输入 | 字段护照 | 12,000 字符 | — |
| FCA 输入 | 投标文件片段 | 15,000 字符 | 供 FCA 做暗标/扫描件/签章直接检查 |

### 3.3 信息隔离设计

BCA 和 FCA **不直接接收招标全文**，只接收 DPA 提取后的结构化数据（审查基准 + 字段护照）。设计理由：

- 避免 27B 在超长输入下注意力分散，遗漏关键判定条件
- BCA 的废标红线判定依赖"条款-响应"对照，结构化输入比全文检索更可靠
- FCA 的隐蔽风险检测依赖字段护照中的特定字段（暗标信息/签章状态），与招标全文无关

## 四、BCA + FCA 并行审查阶段

### 4.1 并行执行

```python
# pipeline.py — Phase 3: BCA + FCA 并行
async def _run_bca_fca_parallel(self) -> None:
    bca_task = asyncio.create_task(self._run_bca())
    fca_task = asyncio.create_task(self._run_fca())
    results = await asyncio.gather(bca_task, fca_task, return_exceptions=True)
    self.bca_result = results[0] if not isinstance(results[0], Exception) else ...
    self.fca_result = results[1] if not isinstance(results[1], Exception) else ...
```

BCA 和 FCA 各自独立调用，互不等待，总耗时取决于较慢的那个（通常各需 2-4 分钟）。

### 4.2 BCA 输入结构（≤22K 字符）

```
【审查任务：业务合规审查】
审查标的：{project_name}（{project_code}）

━━ 审查基准（招标文件提取，只读） ━━
{baseline_text}  ← 截断到 10,000 字符

━━ 字段护照（投标文件提取，只读） ━━
{extracted_fields_text}  ← 截断到 12,000 字符

【输出格式（严格执行）】
第一维度：废标红线审查
  表格：| 检查项 | 招标要求 | 标书实际 | 判定 | 风险等级 | 整改建议 |
  ...（资格准入9项 + ★条款逐条 + 形式要件）

第二维度：中标胜算评估
  表格：| 评分维度 | 满分 | 预计得分 | 依据 |
  ...（商务/技术/价格三类）
```

**BCA 输出结构**：废标红线判定表（逐项 PASS/FAIL/WARNING）+ 中标胜算评估表 + 综合结论。

### 4.3 FCA 输入结构（≤23K 字符）

```
【审查任务：技术取证审查】
审查标的：{project_name}（{project_code}）

━━ 投标文件片段（供暗标/签章直检） ━━
{bid_docs_text}  ← 截断到 15,000 字符

━━ 字段护照（取证相关字段） ━━
{extracted_fields_text}  ← 截断到 8,000 字符

【输出格式（严格执行）】
第一维度：隐蔽风险探测
  ...（暗标脱敏彻底性 / 数据勾稽关系 / 历史版本残留）

第二维度：电子文件安检
  表格：| 文件名 | 检查项 | 判定 | 风险说明 |
  ...（PDF/A合规 / 扫描件质量 / 电子签章 / 文件命名）
```

### 4.4 判定边界硬化

BCA/FCA 的 system prompt 中嵌入完整的**决策树场景分支**，防止 27B 在边界情况下误判：

```
场景 A：字段提取为空
  → 检查文件清单是否存在该文件
    → 文件存在但文本提取失败 → WARNING（需人工核查扫描件）
    → 文件不存在 → FAIL（缺少必要材料）

场景 B：★条款无明确响应文字
  → 判断是否属于"默认响应"条款（技术指标类可隐含响应）
    → 是 → PASS（注明隐含响应依据）
    → 否 → FAIL（缺少明确响应承诺）

场景 C：资质证书有效期临近
  → 距开标日期 < 30 天 → WARNING（建议核查续期情况）
  → 已过期 → FAIL（超出有效期）
```

## 五、ORA 报告编译阶段

### 5.1 报告结构（7 部分 + 附录 A-G）

| 部分 | 章节名 | 内容来源 |
|------|--------|---------|
| 第一部分 | 项目概况与审查摘要 | ORA 编译（从 baseline + BCA/FCA 综合提取） |
| 第二部分 | 废标红线审查 | BCA 结果 |
| 第三部分 | 中标胜算评估 | BCA 结果 |
| 第四部分 | 隐蔽风险探测 | FCA 结果 |
| 第五部分 | 电子文件安检 | FCA 结果 |
| 第六部分 | 审查发现与整改建议 | BCA + FCA 综合 |
| 第七部分 | 线下人工复核事项 | ORA 编译（标注无法从电子文件判定的事项） |
| 附录 A | ★条款响应对照表 | BCA 提取 |
| 附录 B | 资格准入核查表 | BCA 提取 |
| 附录 C | 评分预估明细 | BCA 提取 |
| 附录 D | 隐蔽风险清单 | FCA 提取 |
| 附录 E | 电子文件安检清单 | FCA 提取 |
| 附录 F | 否决项汇总 | BCA + FCA 综合 |
| 附录 G | 整改建议清单 | BCA + FCA 综合 |

### 5.2 证据链编译规则

报告中每个否决项（FAIL）和警告项（WARNING）必须包含完整证据链：

```
否决项格式：
  检查项：{check_item}
  招标要求：{requirement}（引用条款原文，格式：第X页第X.X.X条）
  标书实际：{actual}（DPA 提取的实际值）
  差异：{requirement} vs {actual}
  整改建议：{fix_suggestion}
  支撑材料位置：{evidence_location}
```

### 5.3 AI 痕迹零容忍规则

报告输出文本中禁止出现任何暴露 AI 生成痕迹的表述，包括但不限于：
- "智能体"、"AI 审查"、"大模型"
- "根据我的分析"、"根据算法"
- 连续重复的机械化句式（如"经审查，XX 符合要求。经审查，YY 符合要求。"）

`report_validator.py` 中维护禁用词表，每次 ORA 输出后自动扫描，发现命中则触发重试。

## 六、状态机设计

### 6.1 流水线级状态转换

```
DPA_ROUND_1 ──[人工确认]──► DPA_ROUND_2
                                  │
                         [transition to BCA_BCA]
                                  │
                                  ▼
                            BCA_BCA 阶段
                      ┌─────────────────────┐
                      │  asyncio.gather:    │
                      │  _run_bca() 并行    │
                      │  _run_fca() 并行    │
                      └─────────┬───────────┘
                                │ [两者完成]
                                ▼
                        REPORT_COMPILING
                                │
                                ▼
                              DONE
```

**注意：** `ReviewPhase.BCA_BCA` 是代码中两阶段（BCA 审查 + FCA 审查）的共用阶段标记。`VALID_TRANSITIONS` 表中 `DPA_ROUND_2 → BCA_BCA` 后，Pipeline 在 `BCA_BCA` 阶段内部通过 `asyncio.gather` 同时运行 BCA 和 FCA，两者完成后统一推进到 `REPORT_COMPILING`。

### 6.2 ReviewPhase 枚举（`src/shared/models.py`）

```python
class ReviewPhase(str, Enum):
    DPA_ROUND_1 = "dpa_round_1"          # 招标文件解析 + 审查基准提取
    DPA_ROUND_2 = "dpa_round_2"          # 投标文件解析 + 字段护照提取
    BCA_BCA = "bca_bca"                  # BCA + FCA 并行审查（共用阶段标记）
    REPORT_COMPILING = "report_compiling" # 报告编译
    DONE = "done"

VALID_TRANSITIONS: dict[ReviewPhase, list[ReviewPhase]] = {
    ReviewPhase.DPA_ROUND_1: [ReviewPhase.DPA_ROUND_2],
    ReviewPhase.DPA_ROUND_2: [ReviewPhase.BCA_BCA],
    ReviewPhase.BCA_BCA: [ReviewPhase.REPORT_COMPILING],
    ReviewPhase.REPORT_COMPILING: [ReviewPhase.DONE],
}
```

### 6.3 并行安全持久化（`src/orchestrator/state.py`）

`ReviewStateManager` 实现：
- `asyncio.Lock` 保护并发更新（BCA 和 FCA 同时运行时可能并发写状态）
- 原子写入：先写 `.tmp` 临时文件，再 `rename` 到目标路径（防止写入中断产生损坏的状态文件）
- 接口：`save(state)` / `load()` / `exists()`

### 6.4 断点恢复

`run_full_pipeline.py` 启动时读取 `{project_code}-pipeline_state.json`，根据当前 `phase` 值跳过已完成阶段，从中断点继续。例如，若 `phase == "report_compiling"`，则跳过 DPA 和 BCA/FCA 阶段，直接读取已保存的 BCA/FCA 结果重新编译报告。

```python
class DimensionSummary:

class ReviewReport:
    """最终审查报告"""
    project_code: str = ""
    project_name: str = ""
    review_date: str = ""

    rejection_list: list[dict] = field(default_factory=list)

    # 人工复核事项
    manual_review_items: list[dict] = field(default_factory=list)

@dataclass
class PipelineState:
    """审查流水线状态（断点恢复的持久化单元）"""
    project_code: str = ""
    phase: ReviewPhase = ReviewPhase.DPA_ROUND_1
    review_baseline: Optional[ReviewBaseline] = None
    compliance_results: list[ComplianceResult] = field(default_factory=list)
    report: Optional[ReviewReport] = None
    errors: list[dict] = field(default_factory=list)
```

## 八、Agent 配置

### 8.1 模型配置（通过 `.env`，不硬编码）

```ini
ANTHROPIC_BASE_URL=https://openrouter.ai/api
ANTHROPIC_API_KEY=${OPENROUTER_API_KEY}

# 全部 Agent 统一使用同一模型（或按阶段分配）
PIPELINE_MODEL=qwen/qwen3.6-27b
DPA_MODEL=qwen/qwen3.6-27b
BCA_MODEL=qwen/qwen3.6-27b
FCA_MODEL=qwen/qwen3.6-27b
ORA_MODEL=qwen/qwen3.6-27b
```

### 8.2 温度与 max_tokens 配置

| Agent | Temperature | max_tokens | 说明 |
|-------|-------------|------------|------|
| DPA（Round1 & Round2）| 0.1 | 8,192 | 精确提取，极低温度防止自由发挥 |
| BCA | 0.0 | 8,192 | 审查判断必须确定性，不允许随机性 |
| FCA | 0.0 | 8,192 | 安全检查必须确定性，零容忍误判 |
| ORA | 0.2 | 16,384 | 报告编译适度创造性，大输出容纳 7 章节 + 附录 |

**MAX_RETRY = 3**：每个 Agent 输出格式不通过时最多重试 3 次，超出则标记 `WARNING` 强制保存。

## 九、项目结构

```

├── compare_reports.py      # 多次运行报告对比
│
├── config/
│   └── pipeline.toml       # 流水线参数（max_retry/token上限/截断阈值）
│
├── docs/
│   ├── PRD/                # 产品需求（不修改）
│   │   └── 军用软件标书合规检验智能体指令手册.md
│   └── TDD/                # 技术方案 + 测试方案
│       ├── 军用软件标书合规检验智能体技术方案 v1.md  ← 本文档
│       ├── 军用软件标书合规检验智能体技术方案 v2.md
│       ├── 军用软件标书合规检验智能体测试驱动开发方案 v1.md
│       └── 军用软件标书合规检验智能体测试驱动开发方案 v2.md
│
├── src/
│   ├── shared/
│   │   └── models.py           # 数据模型（ReviewPhase/ReviewBaseline/...）
│   │
│   ├── orchestrator/
│   │   ├── pipeline.py         # ReviewPipeline 主类（四阶段编排，MAX_RETRY=3）
│   │   ├── state.py            # ReviewStateManager（asyncio-safe 原子写入）
│   │   ├── context_builder.py  # Prompt 构建（DPA/BCA/FCA/ORA 四类，含截断逻辑）
│   │   └── report_validator.py # 报告质量校验（7章节 + 附录A-G + AI痕迹检测）
│   │
│   └── agents/
│       ├── client.py           # Claude Agent SDK 封装（call_with_retry）
│       ├── options.py          # AgentOptions 工厂（DPA/BCA/FCA/ORA 温度/token配置）
│       └── prompts/
│           ├── dpa.md          # DPA system prompt（Round1/Round2 通用）
│           ├── bca.md          # BCA system prompt（废标红线 + 中标胜算 + 决策树）
│           ├── fca.md          # FCA system prompt（隐蔽风险 + 电子文件安检 + 决策树）
│           └── ora.md          # ORA system prompt（报告编译 + 7章节模板）

├── tests/
│   ├── conftest.py
│   ├── examples/               # 真实案例文件（只读）
│   ├── fixtures/               # 测试固件（模拟 baseline/extracted_fields）
│   ├── unit/                   # 纯代码测试（零 API 费用）
│   └── quality/                # 真实 API 质量测试
│       └── judge_system.md     # Claude-as-Judge 评估 system prompt
│
└── output/                     # 运行时产出
    └── {project_code}/

        ├── {project_code}-review-baseline.md     # DPA Round1 输出（审查基准）
        ├── {project_code}-extracted_fields.json  # DPA Round2 输出（字段护照）
        ├── {project_code}-bca_result.md          # BCA 审查结果（中间产物）
        ├── {project_code}-fca_result.md          # FCA 取证结果（中间产物）
        └── {project_code}-review-report.md       # 最终审查报告（交付件）
```
