# 标书合规审查系统 — 产品需求文档 (PRD)

> 版本：2.0 | 日期：2026-05-08
> 基于 `demo/biddings-reviewer` 完整业务流程分析

---

## 1. 产品概述

### 1.1 产品愿景

为军用软件投标场景提供 AI 辅助的标书合规审查能力，通过四智能体协作流水线（DPA 文档解析 → BCA+FCA 并行审查 → ORA 报告编译），将标书审查从人工逐页核查升级为自动化、可追溯的智能审查流程。

### 1.2 目标用户

| 用户角色 | 典型场景 | 核心诉求 |
|---------|---------|---------|
| 审查负责人 | 创建审查项目，上传招标文件和投标文件，启动审查 | 快速获得完整审查报告 |
| 标书编制人员 | 根据审查报告中的否决项和缺陷项修改标书 | 清晰的整改建议和优先级 |
| 质量管理人员 | 监控审查进度，审查中间产物 | 实时了解流水线状态和各阶段结果 |

### 1.3 产品范围

**包含：**
- 审查项目管理（创建/查看/删除）
- 招标文件和投标文件上传（PDF/DOCX），后端自动提取文本
- 四阶段 AI 审查流水线（DPA R1 → DPA R2 → BCA+FCA → ORA）
- 格式校验与重试机制（每阶段最多 3 次重试）
- 报告质量评分（0-100 分制，≥60 分通过）
- 流水线实时状态监控（WebSocket）
- 各阶段审查产物查看（审查基准、字段护照、BCA/FCA 结果、最终报告）

**不包含（后续迭代）：**
- PDF 报告导出
- 多轮审查历史对比
- 用户认证与权限管理
- 移动端适配
- 暂停/恢复审查流水线

## 2. 核心业务流程

### 2.1 端到端流程总览

```
用户操作                    系统流水线                           产物
─────────                ──────────                         ──────
创建项目                  → projects 表记录
创建任务                  → tasks 表记录（phase=DOC_UPLOADING）
上传招标文件              → PDF/DOCX 文本提取 → review_documents
上传投标文件(1~N)         → PDF/DOCX 文本提取 → review_documents
启动审查                  → 校验文件完整性
                          │
                          ├─ Phase 1: DPA Round 1 ──────────→ 审查基准（4 张表）
                          │   从招标文件提取 ★号条款/资格准入/评分标准/格式要求
                          │   含格式校验 + 最多 3 次重试
                          │
                          ├─ Phase 2: DPA Round 2 ──────────→ 字段护照（8 张表）
                          │   从投标文件提取公司/资质/社保/审计/人员/业绩/报价/项目名称
                          │   含格式校验 + 最多 3 次重试
                          │
                          ├─ Phase 3: BCA+FCA 并行 ─────────→ BCA结果 + FCA结果
                          │   BCA: 废标红线(6项) + 中标胜算(3项)
                          │   FCA: 隐蔽风险探测(2项) + 电子文件安检(5项)
                          │   各含格式校验 + 最多 3 次重试
                          │
                          └─ Phase 4: ORA 编译报告 ─────────→ 最终审查报告
                              七章节 + 审查签署 + 附录A-G
                              含报告质量评分(≥60分通过) + 最多 3 次重试
```

### 2.2 流水线状态机

流水线通过 `phase` 和 `status` 两个字段管理状态。

#### phase 枚举与合法转换

```
DOC_UPLOADING ──→ DPA_ROUND1 ──→ DPA_ROUND2 ──→ BCA_FCA_RUNNING ──→ REPORT_COMPILING ──→ COMPLETED
                                                                               └──→ FAILED（任何阶段失败）
```

**合法转换（VALID_TRANSITIONS）：**

| 当前阶段 | 可转入 |
|---------|--------|
| DOC_UPLOADING | DPA_ROUND1 |
| DPA_ROUND1 | DPA_ROUND2 |
| DPA_ROUND2 | BCA_FCA_RUNNING |
| BCA_FCA_RUNNING | REPORT_COMPILING |
| REPORT_COMPILING | COMPLETED |

任何阶段执行失败时，`phase` 停留在当前阶段，`status` 变为 `failed`，`errorMessage` 记录失败原因。

#### status 枚举

| 值 | 含义 |
|----|------|
| created | 已创建，等待启动 |
| running | 流水线执行中 |
| completed | 流水线已完成 |
| failed | 流水线失败 |

### 2.3 启动审查的前置校验

启动审查前，系统必须校验：

1. 任务状态为 `created`
2. 已上传招标文件（docType=tender，且仅允许 1 份）
3. 至少上传 1 份投标文件（docType=bid，允许 N 份）

校验通过后：
- 更新 `task.status = "running"`, `phase = "DPA_ROUND1"`
- 异步启动流水线（fire-and-forget）
- 通过 WebSocket 推送 `phase_changed` 和 `agent_call_started` 事件

## 3. 四智能体详细业务流程

### 3.1 DPA — 文档解析智能体

#### 3.1.1 角色定位

DPA 是**非结构化文件 → 结构化数据的转换引擎**。它不做审查判断，只做提取和解析。分为两轮执行：

- **Round 1**：从招标文件提取审查基准（4 张表）
- **Round 2**：从投标文件提取字段护照（8 张表）

#### 3.1.2 DPA Round 1 — 审查基准提取

**输入：** 招标文件全文（截断上限 45,000 字符）

**处理逻辑：**

1. 加载 DPA 系统提示词（定义角色、规则、禁止事项）
2. 构建 Round 1 Prompt：招标文件全文 + 四类提取要求
3. 调用 LLM（temperature=0.1, max_tokens=8192）
4. 对输出执行**格式校验**（代码级检查，非 LLM 检查）
5. 格式不通过 → 追加格式修正要求重试（最多 3 次）
6. 最后一次结果即使格式不完美也保留（优雅降级）

**输出：** 审查基准 Markdown（4 张表）

| 表格 | 内容 | 关键字段 |
|------|------|---------|
| A. ★号条款提取 | 招标文件中所有实质性要求 | 条款编号、原文摘要、所在章节、是否接受负偏离、所需支撑材料类型 |
| B. 资格准入条件提取 | 9 项资格条件 | 条件类型、招标要求摘要、所在章节、是否标注废标项 |
| C. 评分标准提取 | 全部评分项 | 评分类别(商务/技术/价格)、评分项名称、满分、评分规则摘要 |
| D. 格式与封装要求提取 | 投标书格式规范 | 要求类型、招标要求摘要、所在章节 |

**★号条款搜索规则：**
- 搜索标记：★、*（加粗）、【★】、(实质性要求)
- 额外捕获：未标★但注明"不接受负偏离"、"视为无效投标"、"按无效投标处理"的，纳入并标注"隐性★条款"

**资格准入 9 项清单：**
1. 军队采购供应商库
2. 信用记录（三项查询）
3. 营业执照（有效期/注册资本/经营范围）
4. 保密资质（等级/有效期/单位名称一致性）
5. 涉密集成资质（如适用）
6. 社保（参保单位/月份覆盖窗口期）
7. 纳税证明（窗口期覆盖）
8. 审计报告（双签双章/无保留意见）
9. 非外资背景

**格式校验规则（DPA Round 1）：**
- 必须包含："★号条款"、"资格准入条件"、"评分标准"、"格式与封装"四张表
- 缺少任何一张表视为格式不通过，触发重试

#### 3.1.3 DPA Round 2 — 字段护照提取

**输入：**
- 投标文件索引表（列出所有文件名、提取字符数、文件状态）
- 关键投标文件内容（优先文件截断 15,000 字符，其他 4,000 字符）
- 审查基准（截断 10,000 字符）

**优先文件关键词：** 投标函、授权、价格构成、开标一览、偏离表、营业执照、保密资质、社保、纳税、审计、承诺、保证金、业绩、售后服务、人员

**处理逻辑：**

1. 构建投标文件索引表（文件名 + 提取字符数 + 状态评估）
2. 按优先级截断文件内容，组装 Prompt
3. 调用 LLM（同 Round 1 配置）
4. 格式校验 + 最多 3 次重试

**输出：** 字段护照 Markdown（8 张表）

| 序号 | 表格 | 内容 | 关键字段 |
|------|------|------|---------|
| 1 | 公司基本信息 | 投标人主体信息 | 公司名称、信用代码、法人、注册资本、成立日期、营业期限、经营范围 |
| 2 | 资质证书信息 | 各类资质证书 | 资质类型、证书编号、等级、有效期起止、持证单位 |
| 3 | 社保与纳税 | 缴纳记录 | 参保单位、缴纳月份/期间、险种/税种 |
| 4 | 审计报告 | 财务审计信息 | 审计年度、事务所、注册会计师、审计意见、双签双章 |
| 5 | 人员与授权 | 关键人员信息 | 角色、姓名、身份证号、社保关系 |
| 6 | 业绩合同 | 历史业绩 | 合同名称、金额、签订日期、标的类别、双方 |
| 7 | 报价信息 | 分项报价 | 分项名称、单价、数量、合价 |
| 8 | 项目名称一致性检查 | 跨文档比对 | 文件名、出现的项目名称、是否与招标文件一致 |

**格式校验规则（DPA Round 2）：**
- 必须包含至少 3 类字段表（公司基本信息、资质证书、社保、审计、报价、项目名称一致性共 6 类中找到 ≥3 类）

#### 3.1.4 文件索引表生成规则

DPA Round 2 和 BCA/FCA 的 Prompt 中会自动生成投标文件索引表：

| 提取字符数 | 状态说明 |
|-----------|---------|
| < 50 且 PDF 文件 | "扫描件PDF，文本未能提取（文件实体存在，需人工查看）" |
| < 50 且非 PDF | "文本极少（可能为空模板或扫描件）" |
| > 5,000 | "已提取 N 字符（内容完整）" |
| > 500 | "已提取 N 字符（内容基本完整）" |
| 其他 | "部分提取 N 字符" |

#### 3.1.5 DPA 异常信号识别

DPA 在提取时同步扫描以下异常信号，发现即标注：

| 信号类别 | 检测内容 |
|---------|---------|
| 文件名信号 | "缺/无/未"→可能缺失；"zzz/匿名"→暗标标记；"副本/草稿/旧/bak"→版本问题；文件名与内容不符→编制失误 |
| 文件大小信号 | PDF<50KB→空白或纯扫描封面；同名docx和pdf差异>5倍→可能非最终版；>50MB→暗标风险 |
| 数据模式信号 | 连续多年数据完全相同→复制粘贴未更新；整齐整数→占位符；偏离常识→计算错误；表格列/行数与表头不符→格式错误 |
| 时间信号 | 日期为周末/节假日→编造可能；早于招标文件发布日→使用旧模板；多文件同日期→集中补签风险 |

#### 3.1.6 DPA 信息隔离规则

DPA 必须严格遵守：

1. 招标文件中的"示例"、"如"、"假设"引出的内容不是实际要求 → 输出时注明"此为招标文件示例值，非实际要求"
2. "从提取文本中未找到 X" ≠ "X 不存在"
3. 概念区分表（严格使用）：

| 表述 | 含义 | 使用场景 |
|------|------|---------|
| "未从提取文本中发现" | 文本提取失败，文件可能存在 | 扫描件 PDF |
| "文件清单中不存在" | 投标人未提交该文件 | 确定缺失 |
| "文件标注'缺'" | 投标人主动声明缺失 | 自知缺失 |
| "需人工复核" | 电子提取无法完成 | 扫描件/签章/元数据 |

### 3.2 BCA — 业务审查智能体

#### 3.2.1 角色定位

BCA 是**废标判定 + 得分预测专家**。负责废标红线审查（6 项检查）和中标胜算评估（3 项评估）。任何可能导致废标的问题都不能放过；任何失分风险都必须明确指出。

#### 3.2.2 BCA 输入

| 输入项 | 截断上限 | 说明 |
|--------|---------|------|
| 投标文件索引表 | — | 用于区分"文件存在但无法提取"与"文件缺失" |
| 审查基准（招标要求） | 12,000 字符 | DPA Round 1 输出 |
| 投标文件提取字段 | 12,000 字符 | DPA Round 2 输出 |

**调用参数：** temperature=0.0, max_tokens=8192

#### 3.2.3 维度一：废标红线审查（6 项检查）

**检查 1：资格准入合规性（9 项逐项核验）**

逐项检查 9 项资格条件（军队采购供应商库、信用记录、营业执照、保密资质、涉密集成资质、社保、纳税证明、审计报告、非外资背景），每项输出格式：

```
检查项：{名称}
判定：PASS / FAIL / WARNING
招标要求：{原文摘要，注明章节/条款号}
标书实际：{从DPA提取字段中获取的实际值，注明来源文件}
证据位置：{来源文件/页码范围}
是否否决项：是/否
详细说明：{判定依据}
整改建议：{如FAIL，给出具体可操作的整改措施}
```

**检查 2：投标保证金与授权文件**

- 保证金三要素：金额、支付账户、到账时间
- 授权委托书五要素：格式、法人/代理人信息、委托权限、日期

**检查 3：项目名称一致性检查（必做，不可跳过）**

逐文件核对投标文件中出现的项目名称是否与招标文件完全一致。特别注意：版本号（"二次"/"三次"）、括号全角/半角、项目编号数字差异。不一致 → FAIL（否决项——响应错误项目）。

**检查 4：★号条款响应对撞矩阵**

逐条★条款输出对撞结果：

| 字段 | 说明 |
|------|------|
| ★条款编号 | 条款标识 |
| 招标要求 | 原文要求 |
| 标书响应 | 投标文件的响应自述 |
| 支撑材料 | 从投标文件提取的实际值 |
| 偏离判定 | 无偏离/正偏离/负偏离/无法判定(需人工复核)/不适用/虚假响应 |
| 是否否决项 | 致命判定：不接受负偏离的★条款出现负偏离 → 否决项 |

对撞规则：**响应自述 vs 支撑材料实际值 vs 招标要求**，三方比对。

**检查 5：反串通与反雷同筛查**

- 文档元数据残留（作者/公司名/修改记录）
- 图片 EXIF 信息
- 文件哈希（多投标人场景）

**检查 6：形式要件与附属文件**

- 投标书格式、签章完整性、日期一致性
- 声明书与承诺函完整性、条款确认

#### 3.2.4 维度二：中标胜算评估（3 项评估）

| 评估项 | 内容 |
|--------|------|
| 3.1 商务响应竞争力 | 评分项 × 满分 × 预估得分 × 失分项说明 × 改进建议 |
| 3.2 技术方案专业度 | 评分维度 × 满分 × 预估得分 × 评估依据 |
| 3.3 经济合理性 | 算术校验(单价×数量=合价)、大小写一致性、异常低价预警、限价检查 |

#### 3.2.5 BCA 判定边界硬化（强制决策树）

**场景 A：提取字段为空时的判定**

```
该字段在DPA提取结果中是否为空？
├─ 是 → 查文件清单：文件是否存在？
│   ├─ 文件清单中存在 → WARNING（"文件存在但文本未能提取，需人工复核"）
│   ├─ 文件名含"缺" → FAIL（"投标人自标注缺失"）
│   └─ 文件清单中不存在 → FAIL（"文件缺失"）
└─ 否 → 正常比对判定
```

**场景 B：★号条款偏离判定**

```
支撑材料中是否能获取到对应数据？
├─ 能获取 → 比较实际值 vs 招标要求
│   ├─ 完全符合 → PASS / 无偏离
│   ├─ 超过要求 → 正偏离
│   ├─ 不满足 → 是否接受负偏离？
│   │   ├─ 接受 → 负偏离（计入缺陷项）
│   │   └─ 不接受 → 负偏离（否决项）
│   └─ 响应自述与支撑材料矛盾 → 虚假响应（否决项）
└─ 不能获取（PDF扫描件） → "无法判定（需人工复核）"
    └─ 若为★号且不接受负偏离 → 否决项风险，标注"无法判定，建议立即人工核验"
```

**场景 C：资质有效期判定**

```
资质证书有效期截止日 vs 投标截止日
├─ > 投标截止日+30天 → PASS
├─ > 投标截止日 但 < +30天 → WARNING（临期风险）
├─ < 投标截止日 → FAIL（否决项——资质过期）
└─ 无法确定截止日 → WARNING（需人工复核）
```

#### 3.2.6 BCA 证据链锚定规则

**每个 FAIL 判定必须包含完整证据链（缺一不可）：**

1. 招标要求原文位置（章节/条款号/页码）
2. 投标文件实际值（从 DPA 提取字段中获取的原值，不得改写）
3. 差异点描述（具体要求 vs 实际的逐字对比）
4. 来源文件名（投标文件中具体哪个文件）

**缺少以上任何一环的 FAIL 判定无效，必须降级为 WARNING 并标注"证据链不完整，需人工复核"。**

#### 3.2.7 BCA 跨文档交叉验证规则

以下字段必须在所有投标文件中交叉比对：

1. **项目标识一致性**：项目名称/编号/包号/采购方式 → 任一不一致 → FAIL
2. **投标人身份一致性**：营业执照 vs 授权委托书 vs 承诺函中的公司全称/信用代码/法人 → 不一致 → FAIL
3. **报价数据一致性**：开标一览表 vs 价格构成表 vs 投标函中总价/分项合计/大小写 → 不一致 → FAIL
4. **资质信息一致性**：资质证书 vs 投标函 vs 评分索引表中的证书编号/等级/有效期 → 不一致 → 标注差异

#### 3.2.8 BCA 负向信号识别清单

审查时同步扫描以下信号：

| 信号类别 | 信号内容 |
|---------|---------|
| 资质信号 | 资质临期(<3个月)、持证单位与营业执照不一致、多个资质集中到期、证书编号格式异常 |
| 人员信号 | 项目经理社保不在投标单位(挂靠)、同时期参与多项目(人员复用)、身份证号校验码不正确 |
| 财务信号 | 审计报告非无保留意见、CPA签名为打印体、连续三年财务数据完全相同(复制粘贴)、纳税月份不匹配 |
| 程序信号 | 投标函签署日期在招标公告前、多个承诺函签署日期为节假日、授权委托书委托期限不足 |

#### 3.2.9 BCA 格式校验规则

- 必须包含 PASS 或 FAIL 判定
- 检查项数量 ≥ 2（否则视为遗漏）
- 必须包含"否决项"或"缺陷项"汇总
- 不得包含模糊用语："可能""或许""大概""似乎"

#### 3.2.10 BCA 信息隔离规则

1. "未从提取文本中发现" ≠ "文件缺失" — 必须对照文件清单判断
2. BCA 不负责确定文件提取技术细节 — 只基于 DPA 提取结果进行合规判定
3. 信息不足时使用 WARNING + "需人工复核"，不得使用 FAIL

### 3.3 FCA — 技术取证审查智能体

#### 3.3.1 角色定位

FCA 是**暗标还原攻击 + 电子文件安检专家**。用攻击者视角寻找标书中可能被专家委员会发现的技术漏洞。FCA 不审查内容合规性（那是 BCA 的职责），只检查文件层面的技术风险。

#### 3.3.2 FCA 输入

| 输入项 | 截断上限 | 说明 |
|--------|---------|------|
| 投标文件索引表 | — | 文件清单 |
| 投标文件合并文本 | 15,000 字符 | 每个文件截断 12,000 字符后合并 |
| 提取字段 | 8,000 字符 | DPA Round 2 输出 |

**调用参数：** temperature=0.0, max_tokens=8192

#### 3.3.3 维度一：隐蔽风险探测（2 项）

**检查 1：暗标脱敏彻底性（7 项逐一检查）**

| 序号 | 检查项 | 致命判定 |
|------|--------|---------|
| 1 | 公司名称/Logo 清除 | 正文出现公司名称 → 否决项 |
| 2 | 图片 EXIF/XMP 元数据 | 检出投标人信息 → WARNING |
| 3 | PDF 遮盖层还原测试 | 遮盖层下有敏感信息 → 否决项 |
| 4 | 矢量图文本节点检测 | SVG/EPS/EMF 中嵌入文本 → WARNING |
| 5 | Word/PDF 文档属性 | 属性中含投标人信息 → WARNING |
| 6 | 栅格化终验（300dpi→OCR） | OCR 提取到敏感词 → 否决项 |
| 7 | 水印/页眉页脚 | 残留水印/页眉页脚 → WARNING |

每项输出格式：

```
检查项：{名称}
判定：PASS / FAIL / WARNING
检查方法：{使用的检查手段}
检出位置：{文件名/页码范围}
检出内容：{实际检出内容}
是否否决项：是/否
风险说明：{具体分析}
```

**检查 2：内部数据勾稽关系（4 项双向核对）**

| 核验方向 | 来源 A | 来源 B |
|---------|--------|--------|
| 人员 → 报价 | 人员配置数量 | 报价中人员费用行数 |
| 设备 → 清单 | 技术方案设备型号 | 报价清单设备数量 |
| 进度 → 函件 | 甘特图工期 | 投标函工期承诺 |
| Excel → PDF | 报价表数值 | 导出 PDF 中数值 |

输出表格：| 核验方向 | 来源A | 数据A | 来源B | 数据B | 一致性 | 差异百分比 | 差异说明 |

#### 3.3.4 维度二：电子文件安检（5 项）

| 检查项 | 内容 |
|--------|------|
| 5.1 文件格式与平台兼容性 | PDF/A 标准、字体嵌入、颜色空间、禁止内容(JavaScript/Flash)、文件大小 |
| 5.2 扫描件质量 | 分辨率(≥300dpi)、OCR 文本层、图像歪斜/黑边/遮挡/透印 |
| 5.3 电子签章合规 | CA 证书链、有效期、时间戳、签名算法(SM2/RSA-SHA256)、签章位置、多页独立性 |
| 5.4 文件命名与组织 | 命名规则、信号词检测("缺"/"无"/"未"/"zzz"/"匿名"/"副本"/"草稿"/"旧"/"bak") |
| 5.5 暗标反还原测试 | 删除 Annotation→OCR、开启 OCG 图层、栅格化 300dpi→OCR |

#### 3.3.5 FCA 判定边界硬化

**场景 A：暗标脱敏检出判定**

```
是否检出投标人身份信息？
├─ 检出公司全称/法人/项目编号 → FAIL（否决项——暗标失效）
├─ 检出人员姓名（明标区域除外） → FAIL（否决项——暴露身份）
├─ 检出模糊品牌/地区/特征词 → WARNING
├─ 检出原始文档作者/公司属性 → WARNING（元数据残留）
└─ 未检出任何身份信息 → PASS
```

**场景 B：电子签章合规判定**

```
签章验证结果如何？
├─ CA证书链完整 + 有效期内 + 时间戳有效 + 算法合规 → PASS
├─ CA证书链完整 + 临期(<30天) + 其他合规 → WARNING
├─ CA证书链断裂 / 证书过期 / 非认可CA / 无签章 → FAIL（否决项）
├─ 弱算法(SHA-1/MD5) → WARNING
└─ 扫描件无法验证 → 无法判定（需人工复核）
```

**场景 C：数据勾稽关系核验判定**

```
两处数据是否一致？
├─ 完全一致 → PASS
├─ 差异 < 0.1%（舍入误差）→ PASS（标注"可接受的精度差异"）
├─ 差异 0.1%-1% → WARNING
├─ 差异 > 1% → FAIL（数据矛盾）
└─ 其中一处无法提取 → 无法判定（需人工复核）
```

**场景 D：文件扫描件质量判定**

```
扫描件各项指标如何？
├─ ≥300dpi + OCR文本层 + 无歪斜遮挡 → PASS
├─ ≥200dpi 但 <300dpi → WARNING（边缘可用）
├─ <200dpi / 无OCR层 → WARNING
├─ 大面积遮挡/歪斜/透印 → FAIL
└─ 照片而非扫描件 → FAIL（不符合要求）
```

#### 3.3.6 FCA 异常信号识别清单

| 信号类别 | 检测内容 |
|---------|---------|
| 文件结构信号 | PDF页数异常(<10或>500)、目录页码不对应、多版本同名文件、文件名含"副本/草稿/旧/bak/test"、文件名含"缺/无/未" |
| 文件内容信号 | PDF内嵌JavaScript/外部链接(→FAIL)、字体未嵌入、文档属性含投标人信息、修订模式痕迹未清除、OCG图层藏有文本 |
| 签章信号 | 多页签章序列号相同(→FAIL复制粘贴)、签章遮挡文本、签章日期晚于截止日(→FAIL)、CA非认可列表 |
| 跨文档数据信号 | 技术方案设备型号 vs 报价清单不一致、人员数量 vs 报价行数不一致、工期不一致、Excel vs PDF数值差异 |

#### 3.3.7 FCA 格式校验规则

- 必须包含 PASS/FAIL/WARNING 判定
- 检查项数量 ≥ 2（或 PASS/FAIL/WARNING 出现次数 ≥ 6）
- 必须包含"文件命名"检查
- 不得包含模糊用语

#### 3.3.8 FCA 信息隔离规则

1. "未从提取文本中发现" ≠ "文件不存在" — 对照文件清单判断
2. FCA 不审查内容合规性 — 只检查文件层面的技术风险
3. FCA 不评估商务竞争力 — 不输出评分预测
4. 需要专用工具才能判定的事项（CA证书链验证、EXIF提取、文件哈希）→ 标注"需人工使用专用工具复核"
5. 扫描件无法提取文本时，暗标脱敏检查标注"无法判定"而非 PASS

### 3.4 ORA — 报告编译智能体

#### 3.4.1 角色定位

ORA 是**审查流程的导演和报告的最终编辑者**。它不进行新的审查判断，只将 BCA 和 FCA 的审查结果填入标准模板，编译为最终审查报告。

#### 3.4.2 ORA 输入

| 输入项 | 截断上限 | 说明 |
|--------|---------|------|
| 招标文件摘要 | 4,000 字符 | 提取项目名称、编号等基本信息 |
| 审查基准 | 6,000 字符 | DPA Round 1 输出 |
| BCA 审查结果 | 12,000 字符 | 废标红线 + 中标胜算 |
| FCA 审查结果 | 12,000 字符 | 隐蔽风险 + 电子文件安检 |

**调用参数：** temperature=0.2, max_tokens=16384

#### 3.4.3 报告结构（七章节 + 审查签署 + 附录A-G）

报告必须严格按以下顺序输出，跳过任何部分将被打回重新编译：

**第一部分：项目概况与审查摘要（≥200字）**
- 1.1 项目基本信息表（项目名称/编号/投标人/报价/采购方式/审查日期）
- 1.2 审查结论总览表（四维度：废标红线/中标胜算/隐蔽风险/电子文件安检 × 状态/核心结论/风险等级）
- 1.3 评审依据表
- 审查摘要段落（200-400字）

**第二部分：废标红线审查（≥300字）**
- 2.1 资格准入合规性（9项表格）
- 2.2 投标保证金核查表 + 授权委托书检查表
- 2.3 ★号条款响应对撞矩阵
- 2.4 反串通与反雷同筛查
- 2.5 形式要件与附属文件

**第三部分：中标胜算评估（≥200字）**
- 3.1 商务响应得分预测表
- 3.2 技术方案专业度评分预测表
- 3.3 经济评审与价格分析表

**第四部分：隐蔽风险探测（≥200字）**
- 4.1 暗标脱敏检查表
- 4.2 数据勾稽关系核验表

**第五部分：电子文件安检（≥200字）**
- 5.1 电子文件技术合规检查表
- 5.2 扫描件质量评估表
- 5.3 电子签章有效性验证表
- 5.4 文件命名与组织检查
- 5.5 暗标反还原测试

**第六部分：审查发现与整改建议（≥200字）**
- 6.1 否决项清单（问题描述/对应招标条款/判定依据/整改要求/责任方/期限）
- 6.2 缺陷项与改进建议（问题描述/风险等级/整改建议/是否影响评分）
- 6.3 综合审查结论（审查综述 300-500字）+ 投标建议（三选一）

**第七部分：线下人工复核事项**
- 6 项复核表：打印质量、公章签章、骑缝章密封、正副本、封面目录、开标材料

**审查签署**
- 审查人/复核人/批准人签字栏（留空）

**附录A-G（必须全部生成）**

| 附录 | 内容 | 对应正文 |
|------|------|---------|
| 附录A | 资格准入合规审查明细 | 2.1 节 |
| 附录B | 元数据与反串通扫描详情 | 2.4 节 |
| 附录C | 电子投标技术合规检查详情 | 5.1 节 |
| 附录D | 电子签章验证详情 | 5.3 节 |
| 附录E | 暗标还原攻击测试详情 | 4.1/5.5 节 |
| 附录F | 数据勾稽关系核验详情 | 4.2 节 |
| 附录G | 证据文件索引 | 全部 |

#### 3.4.4 审查结论用语规范

**审查状态：**

| 维度 | 状态用语 |
|------|---------|
| 废标红线 | `合格`（无否决项）/ `存在风险`（有否决项） |
| 中标胜算 | `优`（≥90%）/ `良`（≥70%）/ `中`（≥50%）/ `低`（<50%） |
| 隐蔽风险 | `严谨`（无冲突、脱敏彻底）/ `存在瑕疵`（有非致命不一致） |
| 电子文件安检 | `合格`（全部通过）/ `存在风险`（有不合规项） |

**风险等级：**

| 等级 | 含义 |
|------|------|
| 高 | 含否决项，不修复直接废标 |
| 中 | 无否决项但存在失分风险 |
| 低 | 仅形式规范问题 |

**投标建议（强制三选一）：**

| 建议 | 条件 |
|------|------|
| 建议递交 | 无否决项，中标胜算≥良，其他维度无高风险 |
| 有条件递交 | 存在可修复的否决项或高风险项，须列出具体条件 |
| 不建议递交 | 存在不可修复的否决项（资质永久缺失、★条款无法补救的负偏离） |

#### 3.4.5 ORA 证据链编译规则

1. 报告中每个结论必须能从 BCA/FCA 结果追溯到原始证据
2. 每个否决项必须包含：招标条款编号(原文引用) + 判定依据摘要 + 证据来源文件 + 整改要求(具体操作步骤)
3. 每个数值判定必须标注单位
4. 不得凭空创造不存在于 BCA/FCA 结果中的结论
5. BCA/FCA 标注为"需人工复核"的项，报告中必须原样保留，不得改为确定结论

#### 3.4.6 ORA 信息隔离规则

1. ORA 是"报告编译者"而非"审查者" — 不增加新的审查判断
2. BCA/FCA 结果矛盾时，两处判定都保留，标注"跨智能体结论矛盾，需人工仲裁"
3. 招标文件中的"示例""如""假设"不是实际要求，BCA/FCA 引用示例值作依据时需去除
4. 不得从招标文件中自行提取 BCA/FCA 未发现的条款加入报告
5. 不得升级或降级 BCA/FCA 的判定结论

## 4. 格式校验与重试机制

### 4.1 两层校验体系

系统采用两层校验确保输出质量：

| 层级 | 校验对象 | 校验方式 | 失败处理 |
|------|---------|---------|---------|
| 第一层：格式校验 | DPA R1/R2、BCA、FCA 的输出 | 代码级正则匹配 | 追加格式修正要求，重试最多 3 次 |
| 第二层：质量评分 | ORA 的最终报告 | 结构+表格+AI痕迹+标题编号+投标建议综合评分 | 追加问题清单，重试最多 3 次 |

### 4.2 第一层：格式校验（各 Agent）

#### DPA Round 1 格式校验

| 检查项 | 规则 |
|--------|------|
| 四张表完整性 | 必须包含"★号条款""资格准入条件""评分标准""格式与封装" |

#### DPA Round 2 格式校验

| 检查项 | 规则 |
|--------|------|
| 字段表完整性 | 6 类字段表（公司基本信息/资质证书/社保/审计/报价/项目名称一致性）中至少找到 3 类 |

#### BCA 格式校验

| 检查项 | 规则 |
|--------|------|
| 判定存在性 | 必须包含 PASS 或 FAIL 或"合格"或"不合格" |
| 检查项数量 | 检查项≥2 个 |
| 汇总存在性 | 必须包含"否决项"或"缺陷项"汇总 |
| 模糊用语 | 不得包含"可能""或许""大概""似乎" |

#### FCA 格式校验

| 检查项 | 规则 |
|--------|------|
| 判定存在性 | 必须包含 PASS 或 FAIL |

| 检查项 | 规则 |
|--------|------|

| 投标建议 | 必须包含"建议递交""有条件递交""不建议递交"之一 |
| AI 痕迹 | 不得包含"根据指令手册""按照SOP""作为ORA/BCA/FCA/DPA""智能体判断""已按模板""审查完成""提取完毕" |

### 4.3 第二层：报告质量评分

对 ORA 最终报告进行综合质量评估（满分 100 分）：

| 评分维度 | 扣分规则 |
|---------|---------|
| 章节结构 | 每缺少 1 个关键章节扣 10 分 |
| 表格完整性 | 每缺少 1 个数据表扣 8 分 |
| AI 痕迹 | 每检出 1 处 AI 痕迹扣 15 分 |
| 投标建议 | 缺少投标建议扣 15 分 |
| 报告长度 | <500 字扣 20 分，<1500 字扣 10 分 |

**AI 痕迹检测模式（120+ 模式）：**

| 类别 | 示例 |
|------|------|
| 指令手册引用 | "根据指令手册""按照SOP""依据本手册" |
| Agent 身份暴露 | "作为DPA""智能体判断""AI审查""自动审查" |

**通过条件：** 分数 ≥ 60 **且** 缺少章节 ≤ 2

### 4.4 重试机制

**每个阶段最多 3 次重试：**

```
for attempt in range(MAX_RETRY):  # MAX_RETRY = 3
    result = call_llm(prompt)
    if result 为空:
        continue  # 空响应，直接重试
    issues = validate_format(result)
    if issues 为空:
        保存结果 → return
    # 格式不通过，追加修正要求
    if attempt < MAX_RETRY - 1:
        prompt = original_prompt + 格式修正要求(issues)
# 最后一次结果即使格式不完美也保留（优雅降级）
```

**格式修正 Prompt 模板：**

```
{原始Prompt}

━━━━━━━━━━━━━━━━━━━━━━━━━━
⚠ 格式修正要求（上一轮输出存在以下格式问题）
━━━━━━━━━━━━━━━━━━━━━━━━━━
- {issue_1}
- {issue_2}
...

请重新输出，务必修正上述格式问题。其余内容不变。
```

**报告编译的特殊重试逻辑：**

- 额外检查：报告长度 < 300 字符时视为无效，等待 2 秒后重试
- 质量不通过时追加问题清单到 Prompt，等待 2 秒后重试
- 最后一次结果即使质量不完全达标（< 60 分）也输出（优雅降级）

## 6. 文件处理流程

### 6.1 文件上传

**允许格式：** `.pdf`, `.docx`, `.doc`
**大小限制：** 单文件 ≤ 100MB

**约束规则：**
- 每个任务仅允许 1 份招标文件（docType=tender），重复上传返回 409
- 投标文件（docType=bid）可上传多份
- 上传顺序记录在 `uploadOrder` 字段

### 6.2 文本提取

后端收到上传文件后：
1. 保存原始文件到 `uploads/reviewer/{taskId}/{sanitizedFileName}`
2. 使用 pdf-parse（PDF）或 mammoth（DOCX）提取文本
3. 将文本存入 `review_documents.textContent`
4. 计算字符数存入 `charCount`

**charCount 语义：**

| charCount | 含义 |
|-----------|------|
| null | 文本提取失败 |
| < 50 且为 PDF | 可能是扫描件（文本未能提取） |
| ≥ 5,000 | 内容完整 |
| ≥ 500 | 内容基本完整 |

### 6.3 文本截断策略

各阶段 Prompt 构建时对输入文本有不同的截断上限：

| 阶段 | 输入 | 截断上限 |
|------|------|---------|
| DPA R1 | 招标文件全文 | 45,000 字符 |
| DPA R2 | 优先投标文件 | 15,000 字符/文件 |
| DPA R2 | 其他投标文件 | 4,000 字符/文件 |
| DPA R2 | 审查基准 | 10,000 字符 |
| BCA | 审查基准 | 12,000 字符 |
| BCA | 提取字段 | 12,000 字符 |
| FCA | 投标文件合并文本 | 15,000 字符 |
| FCA | 提取字段 | 8,000 字符 |
| ORA | 招标文件摘要 | 4,000 字符 |
| ORA | 审查基准 | 6,000 字符 |
| ORA | BCA 结果 | 12,000 字符 |
| ORA | FCA 结果 | 12,000 字符 |

**截断函数行为：**

```python
def _truncate(text, max_chars=20000):
    if not text: return "[无内容]"
    if len(text) <= max_chars: return text
    return text[:max_chars] + f"\n\n... [已截断，原文共{len(text)}字符]"
```

## 7. Agent 调用配置

### 7.1 各 Agent 参数

| Agent | temperature | max_tokens | 说明 |
|-------|------------|------------|------|
| DPA | 0.1 | 8192 | 低温度确保提取精确性 |
| BCA | 0.0 | 8192 | 零温度确保判定一致性 |
| FCA | 0.0 | 8192 | 零温度确保判定一致性 |
| ORA | 0.2 | 16384 | 略高温度增加报告自然度，大 token 量确保报告完整 |

### 7.2 模型选择优先级

```
{ROLE}_MODEL → PIPELINE_MODEL → ANTHROPIC_MODEL
```

即：先查角色专属模型配置（如 DPA_MODEL），没有则查统一流水线模型（PIPELINE_MODEL），再没有则查全局默认模型（ANTHROPIC_MODEL）。

### 7.3 LLM 调用日志

每次 LLM 调用都记录到 `llm_call_logs` 表：

| 字段 | 说明 |
|------|------|
| agentRole | 调用的 Agent 角色（dpa/bca/fca/ora） |
| model | 实际使用的模型名称 |
| inputTokens | 输入 token 数 |
| outputTokens | 输出 token 数 |
| latencyMs | 调用耗时（毫秒） |
| error | 错误信息（调用失败时） |

## 10. 验收标准

### 10.1 P0 功能验收

1. 用户可创建审查项目并创建任务
2. 用户可上传招标文件（1 份）和投标文件（多份），系统自动提取文本
3. 用户启动审查后，流水线按 DPA R1 → DPA R2 → BCA+FCA(并行) → ORA 顺序执行
4. 流水线执行过程中，前端实时显示当前阶段和 Agent 调用状态
5. 每个阶段完成后，用户可立即查看该阶段的审查产物
6. 最终生成的审查报告包含完整的七章节结构 + 审查签署 + 附录 A-G
7. 报告中包含明确的投标建议（建议递交/有条件递交/不建议递交）

### 10.2 报告质量标准

1. 报告必须包含 7 个章节和审查签署
2. 报告必须包含附录 A-G（全部 7 个附录）
3. 报告不得包含 AI 痕迹表述（"根据指令手册""智能体判断"等 120+ 模式）
4. 所有否决项必须有完整证据链（招标条款 → 判定依据 → 证据来源）
5. 报告质量评分 ≥ 60 分且缺少章节 ≤ 2 视为通过
6. 标题编号连续且一致（H2 "第X部分" 顺序正确，H3 "X.Y" 与父章节匹配）

### 10.3 业务逻辑验收

1. DPA 提取结果中不得将"未提取到"等同于"文件缺失"
2. BCA 对空字段的判定必须经过决策树（查文件清单 → 判定 WARNING/FAIL）
3. ★号条款不接受负偏离时出现负偏离 → 必须判定为否决项，不得降级
4. BCA/FCA 的 FAIL 判定必须有完整证据链，否则降级为 WARNING
5. BCA+FCA 结果矛盾时，报告中两处判定都保留，标注"需人工仲裁"
6. 报告中不得升级或降级 BCA/FCA 的原始判定结论

## 11. 术语表

| 术语 | 含义 |
|------|------|
| DPA | 文档解析智能体（Document Parsing Agent）— 非结构化→结构化转换引擎 |
| BCA | 业务审查智能体（Business Compliance Agent）— 废标判定+得分预测专家 |
| FCA | 技术取证审查智能体（Forensic Compliance Agent）— 暗标还原攻击+电子文件安检 |
| ORA | 报告编译智能体（Orchestration & Report Agent）— 流程导演+报告编辑 |
| ★条款 | 招标文件中标注★的实质性要求条款，偏离可能导致废标 |
| 废标红线 | 会导致投标被否决的硬性违规项（资格准入/★条款/保证金等） |
| 字段护照 | 从投标文件中提取的关键结构化数据集合（8 张表） |
| 勾稽关系 | 不同文件/表格之间数据的一致性关系（如人员数量 vs 报价行数） |
| 否决项 | 不修复直接导致废标的严重问题 |
| 缺陷项 | 不导致废标但存在失分风险的问题 |
| 暗标 | 隐藏投标人身份的投标文件，需彻底脱敏 |
| 证据链 | 判定的完整依据链条（招标要求→标书实际→差异对比→来源文件） |
| 格式校验 | 代码级输出质量检查（非 LLM 检查），确保输出包含必要结构和判定 |
| 报告质量评分 | 对最终报告的综合质量评估（0-100分，≥60分通过） |
